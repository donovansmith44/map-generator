# Historical Bible Atlas Rendering Architecture Specification

**Status:** Proposed
**Primary client backend:** WebGL2
**Optional future backend:** WebGPU
**Primary design priorities:** image stability first; 60 fps second; implementation simplicity third

---

## 1. Purpose

This specification defines the interactive rendering architecture for the historical Bible atlas.

The existing Rust workspace already provides the semantic and geometric foundations:

* a content-addressed canonical store;
* shared borders on the unit sphere;
* time as a first-class dimension;
* historical territory morph/split/merge semantics;
* a provider that answers historical render queries;
* existing viewport culling using spherical caps;
* a single level-of-detail law based on approximately half an on-screen pixel;
* styled scenes;
* two projections;
* an existing `SceneEncoder` abstraction;
* an existing `SvgEncoder`.

Those components remain authoritative.

This specification adds a retained interactive renderer whose fundamental property is:

> **The interactive map is a persistent retained scene, not a sequence of independently rendered pictures.**

The renderer must support continuous pan and zoom with a Google-Earth-like interaction model:

* camera motion remains smooth and interactive;
* existing geometry persists between frames;
* asynchronous detail acquisition never blocks interaction;
* detail increases without visible popping;
* labels remain screen-sized and stable;
* camera changes never cause the current image to be discarded and replaced wholesale.

The central distinction is:

> **Camera motion changes the view of the map; it does not cause the map itself to be reconstructed.**

---

# 2. Existing System

The existing architecture consists of:

```text
Canonical Store
    ↓
Historical Provider
    ↓
Styled Scene
    ↓
SceneEncoder
    ↓
SvgEncoder
```

The canonical geometry is content-addressed and shared.

Measured current scale:

* 11,961 border polylines
* 780,281 vertices
* approximately 1,792 features
* approximately 1,200 named areas
* approximately 560 river/line features
* 27 city points
* approximately 1,200 potential area labels plus city and memorial labels
* 104 snapshots
* 89 distinct time stops
* 6 paint layers
* approximately 78 MB JSON source representation
* approximately 9 MB packed raw vertex data

The current viewer requests a complete SVG for a camera position.

During motion it scales a bitmap snapshot of the previous frame and later replaces it with a newly rendered SVG.

That architecture produces the observed visual instability:

```text
previous frame bitmap
    ↓
scaled bitmap
    ↓
coarse SVG
    ↓
fine SVG
```

The new architecture eliminates that representation-swapping cycle.

---

# 3. Design Priorities

The renderer shall optimize, in this order:

1. **Image stability**
2. **60 fps interaction**
3. **Implementation simplicity**

Image stability is the primary requirement even where doing so would permit a theoretically simpler redraw architecture.

---

# 4. Fundamental Rendering Laws

These laws are normative.

## R1 — Camera Continuity

For a fixed semantic scene, a continuous change in:

* camera target;
* camera zoom;
* viewport;
* camera orientation;

shall not invalidate the retained scene.

A camera change may alter:

* GPU projection uniforms;
* visibility of already-retained resources;
* resource demand.

It shall not require a complete scene reconstruction.

---

## R2 — Camera Motion Is Not Scene Reconstruction

Pan and zoom are both camera changes.

A pan changes the camera target.

A zoom changes camera scale.

A combined gesture changes both.

The renderer shall treat all of them as one continuous camera trajectory:

```rust
struct Camera {
    target: SphericalPoint,
    zoom: Zoom,
    viewport: Viewport,
}
```

Conceptually:

```text
pan:
    target₁ → target₂

zoom:
    zoom₁ → zoom₂

pan + zoom:
    target₁, zoom₁ → target₂, zoom₂
```

The renderer must never interpret:

```text
target changed
```

as:

```text
map changed
```

---

## R3 — Existing Content Persists

If a resource was drawable before a camera change, it remains drawable afterward unless it is explicitly evicted according to the residency policy.

Camera motion alone cannot cause the renderer to:

```text
clear scene
fetch new scene
show blank
draw replacement
```

---

## R4 — Acquisition Never Blocks the Frame Loop

Network I/O, resource decoding, GPU upload, label acquisition, and other asynchronous work shall never block the camera animation loop.

The render loop must remain capable of drawing the retained scene while new resources are unavailable.

---

## R5 — Refinement Is Monotonic

A spatial refinement may add geometric fidelity.

It must not visibly destroy existing fidelity merely because a more detailed representation has become available.

---

## R6 — Refinement Is Continuous

Where a coarse and fine representation are refinements of the same geometry, the transition between them shall be mathematically continuous.

At the beginning of a refinement transition, the refined representation must be visually equivalent to the existing representation within the renderer's declared numerical tolerance.

---

## R7 — Existing Semantics Are Not Erased by LOD

The existing project law:

> fidelity may thin a ring, never erase it

is generalized to rendering:

> **refinement may increase fidelity, but it may not cause an already represented semantic or geometric feature to disappear discontinuously.**

---

## R8 — Content Identity Is Independent of View

A geometry's content-addressed identity is independent of:

* camera;
* projection;
* historical year;
* viewport;
* rendering backend.

---

## R9 — Projection Does Not Own Geometry

Canonical geometry remains projection-independent spherical geometry.

Projection is a rendering operation, not part of canonical identity.

---

## R10 — Residency and Visibility Are Distinct

A resource may be resident without currently being visible.

The intended relationship is:

```text
visible resources ⊆ resident resources
```

subject to explicit asynchronous acquisition.

---

# 5. Retained Scene Model

The retained renderer shall not model every frame as a newly generated scene.

It shall maintain:

```text
immutable resources
        +
semantic scene references
        +
GPU residency
        +
persistent label state
        +
camera state
```

The retained representation consists of four conceptual layers.

---

# 6. Canonical Geometry

The existing canonical geometry remains authoritative.

Example:

```rust
struct CanonicalGeometry {
    id: GeometryId,
    primitive: PrimitiveKind,
    vertices: Vec<UnitVec>,
}
```

with:

```rust
#[derive(Clone, Copy, Hash, Eq, PartialEq)]
struct GeometryId(ContentHash);
```

The key invariant is:

> `GeometryId` identifies the geometry's content, not its location in time or its projection.

---

# 7. Resource Representations

A canonical geometry may have multiple rendering representations.

For example:

```rust
struct GeometryRepresentation {
    id: ResourceId,
    geometry: GeometryId,
    detail: DetailLevel,
    geometric_error: GeometricError,
    spherical_bounds: SphericalBounds,
    payload: PackedGeometry,
}
```

The representation itself is content-addressed.

This permits:

```text
same canonical geometry
        ↓
coarse representation
        ↓
fine representation
```

without changing the canonical identity of the geometry.

---

# 8. Scene Manifest

The renderer receives a semantic scene manifest rather than a camera-specific picture.

```rust
struct SceneManifest {
    scene_revision: ContentHash,
    time: Year,
    layers: LayerSet,
    features: Vec<FeatureInstance>,
}

struct FeatureInstance {
    feature: FeatureId,
    geometry: GeometryId,
    lod_chain: LodChainId,
    style: StyleId,
}
```

A scene manifest contains no projected vertices.

It contains no rasterized frame.

It contains no SVG.

---

# 9. Content-Addressed Identity

At minimum, these identities shall exist:

```rust
struct GeometryId(ContentHash);
struct FeatureId(ContentHash);
struct StyleId(ContentHash);
struct LodChainId(ContentHash);
struct ResourceId(ContentHash);
struct SnapshotId(ContentHash);
struct GlyphAtlasId(ContentHash);
struct CorrespondenceId(ContentHash);
```

All persistent caches use these identities.

No cache may fundamentally key resources by:

```text
feature number + zoom
```

or:

```text
year + viewport
```

or:

```text
camera position
```

unless those are merely derived indices over content-addressed resources.

---

# 10. Time Is Not Part of Geometry Identity

Historical time belongs to scene state and temporal correspondence.

It does not belong in the fundamental geometry key.

For example:

```text
year 500 BC → GeometryId H123
year 400 BC → GeometryId H123
year 300 BC → GeometryId H123
```

shall result in one reusable geometry resource.

This is essential because the canonical store already shares geometry across snapshots.

---

# 11. Resource Cache

The client shall maintain an immutable resource cache.

Conceptually:

```ts
interface ResourceCache {
    get(id: ResourceId): ResidentResource | undefined;
    request(id: ResourceId): Promise<ResidentResource>;
    retain(id: ResourceId, reason: RetentionReason): void;
    release(id: ResourceId, reason: RetentionReason): void;
}
```

The interface shall not encode a fixed capacity.

A small implementation may retain everything.

A larger implementation may page resources between:

* network;
* disk;
* CPU memory;
* GPU memory.

The renderer shall not know which implementation is in use.

---

# 12. No Full-Atlas Client Contract

The client shall never depend on an API such as:

```text
loadEntireAtlas()
```

or:

```text
getAllFeatures()
```

as a rendering requirement.

Initial implementation may internally load all available resources for simplicity, but the interface must remain demand-driven:

```rust
trait ResourceProvider {
    fn request_visible(
        &self,
        request: VisibilityRequest,
    ) -> ResourceResponse;
}
```

The same contract must remain valid if the dataset grows by 10× or more.

---

# 13. Small-Data and Large-Data Implementations

The same interfaces must support two implementations.

### Current small-data implementation

```text
all decoded geometry
    ↓
CPU resident
    ↓
GPU resident
```

### Future large-data implementation

```text
visible resource demand
    ↓
spatial pages / tiles
    ↓
disk/network fetch
    ↓
CPU decode
    ↓
GPU residency
```

The distinction is private to the resource/residency layer.

No higher-level interface may assume that the whole atlas fits in memory.

---

# 14. Resource Residency State

Each resource shall have explicit residency state:

```rust
enum ResidencyState {
    Missing,
    Requested,
    CpuResident,
    GpuResident,
    Refining,
    Stable,
    EvictPending,
    Evicted,
}
```

Permitted progression includes:

```text
Missing
   ↓
Requested
   ↓
CpuResident
   ↓
GpuResident
   ↓
Stable
```

and:

```text
Stable(parent)
   ↓
GpuResident(child)
   ↓
Refining(parent, child)
   ↓
Stable(child)
```

No refinement failure may produce:

```text
Stable(parent) → Missing
```

---

# 15. GPU Residency

GPU resources shall be independent from semantic feature objects.

Conceptually:

```ts
interface GpuGeometry {
    resourceId: ResourceId;
    vertexBuffer: WebGLBuffer;
    indexBuffer?: WebGLBuffer;

    vertexCount: number;
    indexCount: number;

    bounds: SphericalBounds;
}
```

A geometry resource may remain resident for many frames while the camera moves.

The same GPU geometry may be used by many historical snapshots.

---

# 16. GPU Buffer Organization

The initial implementation should use buffer arenas rather than creating an independent WebGL buffer for every semantic feature.

Conceptually:

```ts
interface GpuAllocation {
    buffer: WebGLBuffer;
    byteOffset: number;
    byteLength: number;
}
```

with:

```text
ResourceId
    ↓
GpuAllocation
```

The backing allocation mechanism may later be replaced by a paged or tiled implementation.

The semantic interface must not change.

---

# 17. Packed Geometry

The initial vertex representation should remain simple:

```text
float32 x
float32 y
float32 z
```

representing a unit-sphere position.

Premature quantization is not required.

If later measurements demonstrate sufficient benefit, the encoding may change without affecting the semantic geometry identity.

---

# 18. New SceneEncoder

The existing `SceneEncoder` abstraction remains.

Add:

```rust
struct GpuSceneEncoder;
```

alongside the existing:

```rust
struct SvgEncoder;
```

The new encoder produces retained rendering resources rather than a picture.

Conceptually:

```rust
trait SceneEncoder {
    fn encode(&self, scene: &StyledScene) -> EncodedScene;
}
```

and:

```rust
struct EncodedScene {
    manifest: SceneManifest,
    resources: Vec<ResourceDescriptor>,
}
```

---

# 19. Resource Descriptor

A resource descriptor should contain sufficient immutable metadata to support caching and residency:

```rust
struct ResourceDescriptor {
    id: ResourceId,
    kind: ResourceKind,
    byte_length: u64,
    content_hash: ContentHash,

    lod_parent: Option<ResourceId>,
    lod_children: Vec<ResourceId>,

    geometric_error: GeometricError,
    spherical_bounds: SphericalBounds,
}
```

---

# 20. Camera Model

The camera is a first-class persistent client state:

```rust
struct Camera {
    target: SphericalPoint,
    zoom: Zoom,
    viewport: Viewport,
}
```

If the implementation needs orientation explicitly:

```rust
struct Camera {
    target: SphericalPoint,
    orientation: CameraOrientation,
    zoom: Zoom,
    viewport: Viewport,
}
```

The exact camera representation must preserve the existing project camera law.

The same camera law feeds both projections.

---

# 21. Camera Controller

The client shall own a continuous camera controller:

```ts
interface CameraController {
    current: Camera;
    target: Camera;

    update(time: Time): void;
}
```

Input changes the target state.

The controller generates a continuous camera trajectory:

```text
pointer/wheel
    ↓
camera target
    ↓
current camera
    ↓
animation frames
```

Pan is not special-cased separately from zoom at the renderer level.

Both simply alter the camera.

---

# 22. Pan

A pan changes the camera target/orientation.

For a globe:

```text
target₁ → target₂
```

changes which portion of the sphere faces the viewer.

For a flat projection:

```text
target₁ → target₂
```

changes which part of the chart occupies the viewport.

In both cases the underlying canonical geometry is unchanged.

Therefore:

```text
pan
  → camera update
  → GPU transform
```

not:

```text
pan
  → new server-rendered image
```

---

# 23. Zoom

Zoom changes the camera scale under the existing project camera law.

A zoom interaction likewise shall not rebuild the scene.

The renderer must maintain smooth fractional zoom.

There shall be no discrete:

```text
zoom level 4
→ zoom level 5
→ replace scene
```

transition.

---

# 24. Pan + Zoom

A combined user gesture produces one continuous camera state:

```text
Camera(t) =
    {
        target(t),
        zoom(t),
        viewport(t)
    }
```

The renderer samples that state each animation frame.

The scene remains retained while:

```text
target(t)
```

and:

```text
zoom(t)
```

change.

---

# 25. Frame Loop

The interactive frame loop shall contain no blocking acquisition.

Conceptually:

```ts
function frame(now: number) {
    camera.update(now);

    renderer.beginFrame();
    renderer.setCamera(camera);
    renderer.draw(retainedScene);
    renderer.endFrame();

    requestAnimationFrame(frame);
}
```

The frame loop must not await network operations.

It must not perform full scene encoding.

It must not create a bitmap snapshot.

It must not request a fresh SVG for every camera position.

---

# 26. Acquisition Loop

Resource acquisition runs independently:

```ts
async function acquisitionLoop() {
    while (running) {
        const demand =
            retainedScene.computeDemand(camera);

        await resources.ensure(demand);

        retainedScene.commitNewResources();
    }
}
```

The acquisition loop may take substantially longer than one frame.

The frame loop remains interactive throughout.

---

# 27. Remove Bitmap Snapshot Rendering

The following architecture shall be retired:

```text
SVG frame
   ↓
canvas bitmap snapshot
   ↓
scale bitmap during movement
```

The renderer must never depend on a screenshot of the previous frame.

GPU projection exists specifically so the previous rendered image does not need to become a new rendering primitive.

---

# 28. Projection Architecture

Canonical geometry remains in spherical coordinates.

The renderer shall project it at draw time.

Conceptually:

```rust
trait Projection {
    fn project(
        &self,
        point: UnitVec,
        camera: &Camera,
    ) -> ProjectedPoint;
}
```

Implement:

```rust
struct OrthographicGlobeProjection;
struct EquirectangularProjection;
```

The actual GPU implementation shall express the same mathematics in the vertex shader.

---

# 29. GPU Projection

The preferred path is:

```text
canonical unit-sphere vertex
        ↓
GPU vertex shader
        ↓
camera/projection uniforms
        ↓
clip-space vertex
```

The CPU should not repeatedly project every vertex during ordinary camera animation.

A camera change should primarily modify uniforms.

---

# 30. Why Projection Is GPU-Owned

CPU projection per frame would require repeatedly transforming hundreds of thousands of vertices.

Precomputing projected geometry would require maintaining projection-specific resources for:

* different camera positions;
* different zooms;
* different projections.

GPU projection instead permits:

```text
same geometry
+
new uniforms
=
new view
```

This is the required relationship for stable pan and zoom.

---

# 31. Projection Independence

A `GeometryId` shall not distinguish:

```text
orthographic version
```

from:

```text
flat version
```

of the same canonical geometry.

The relationship shall be:

```text
canonical spherical geometry
        ├── orthographic projection
        └── equirectangular projection
```

---

# 32. Shared Camera Law

Both projections shall consume the same semantic camera:

```text
Camera
   ├── OrthographicGlobeProjection
   └── EquirectangularProjection
```

The projections differ only in transformation mathematics.

This ensures that the existing rule:

> page width spans 2 × zoom great-circle degrees on both

continues to govern both.

---

# 33. Globe Culling

The existing precomputed spherical-cap culling remains authoritative.

The provider or resource-demand system may perform:

```text
spherical-cap culling
```

before resources are requested or placed in the draw list.

The CPU should not project every vertex merely to determine ordinary visibility.

---

# 34. Visibility Layers

Visibility is evaluated hierarchically:

```text
provider semantic culling
        ↓
retained resource visibility
        ↓
GPU projection/clipping
```

A resource being resident does not imply it must be rendered.

---

# 35. Level of Detail

The existing project LOD law remains authoritative:

> simplify to approximately half an on-screen pixel at the camera's zoom and page width.

No second independently invented LOD rule shall be added to the client.

The distinction is:

```text
provider:
    which detail is required?

renderer:
    how do I introduce that detail without visual discontinuity?
```

---

# 36. LOD Representation

LOD shall be modeled as an explicit refinement hierarchy:

```rust
struct LodChain {
    base: ResourceId,
    refinements: Vec<ResourceId>,
}
```

Each refinement records how the new representation relates to the old.

---

# 37. Additive Refinement

Where possible, refinement should be additive.

Example:

```text
coarse:
A ─────────────────── B
```

becomes:

```text
fine:
A ── p1 ── p2 ── p3 ── B
```

The existing geometry remains valid at the beginning of the transition.

New detail is introduced by adding vertices or subdividing existing primitives.

---

# 38. Continuous Geometric Refinement

A refinement relationship may specify a correspondence:

```rust
struct GeometryCorrespondence {
    id: CorrespondenceId,
    mapping: CorrespondenceData,
}
```

The renderer may then evaluate:

```text
P(t)
```

where:

```text
P(0) = coarse representation
P(1) = fine representation
```

within numerical tolerance.

---

# 39. No Pure Fade as the Primary LOD Mechanism

The renderer shall not hide arbitrary geometric discontinuities merely by cross-fading:

```text
old alpha → 0
new alpha → 1
```

A fade may be used for lifecycle events such as label appearance.

It is not the fundamental mechanism for spatial geometry refinement.

Spatial refinement must itself be continuous.

---

# 40. Refinement Transaction

A refinement operation shall follow:

```text
1. parent is resident and drawable
2. child is requested
3. child is decoded
4. child is uploaded
5. child is validated
6. child becomes drawable
7. continuous refinement begins
8. child becomes authoritative
9. parent may become evictable
```

At no point may the renderer clear the parent while the child is unavailable.

---

# 41. Refinement Failure

If a child resource fails to load:

```text
parent remains drawable
```

The failure must not alter the existing image.

---

# 42. Polygon Refinement

Polygon refinement should use hierarchical subdivision where possible.

A refined tessellation should derive from the coarse representation rather than being an unrelated triangulation.

The goal is:

```text
coarse representation
        ↓
continuous refinement
        ↓
fine representation
```

without visible topology replacement.

---

# 43. Temporal Semantics

Spatial LOD and historical change are distinct concepts.

A historical change may alter topology:

```text
one territory → two territories
```

or:

```text
A + B → C
```

These require explicit temporal semantics.

---

# 44. Temporal Changes

The temporal model may contain:

```rust
enum TemporalChange {
    Persistent {
        from: FeatureId,
        to: FeatureId,
    },

    Birth {
        feature: FeatureId,
    },

    Death {
        feature: FeatureId,
    },

    Split {
        source: FeatureId,
        descendants: Vec<FeatureId>,
    },

    Merge {
        sources: Vec<FeatureId>,
        destination: FeatureId,
    },

    Morph {
        from: GeometryId,
        to: GeometryId,
        correspondence: CorrespondenceId,
    },
}
```

The temporal compiler determines these relationships.

The renderer executes them.

---

# 45. Historical Scene Changes

A change of historical time shall not necessarily clear the existing scene.

Instead:

```text
old scene
   ↓
new scene requested
   ↓
required resources acquired
   ↓
new scene validated
   ↓
temporal transition begins
   ↓
old scene retired
```

This gives historical transitions the same stability properties as camera motion.

---

# 46. Labels

Labels shall be a retained subsystem separate from ordinary geometry.

Conceptually:

```ts
interface LabelInstance {
    feature: FeatureId;
    text: GlyphRun;
    anchor: SphericalAnchor;
    style: LabelStyle;
    priority: LabelPriority;

    placement: LabelPlacement;
    state: LabelVisibilityState;
}
```

---

# 47. Glyphs

A glyph is the visual form used to draw a character from a font.

The text:

```text
Jerusalem
```

becomes a sequence of glyphs which are rendered by the GPU.

The client may use:

```text
font data
    ↓
text shaping
    ↓
glyph metrics
    ↓
glyph atlas
    ↓
GPU label quads
```

---

# 48. GPU Text

DOM/SVG text is not required.

The renderer shall permit GPU-rendered text while preserving the existing typography abstraction.

Styles remain data:

```rust
struct LabelStyle {
    family: FontFamilyId,
    weight: FontWeight,
    italic: bool,
    tracking: f32,
    advance: AdvanceModel,
    size: ScreenLength,
}
```

The renderer may compile those declarations into GPU resources.

Typography semantics shall not be embedded in rendering code.

---

# 49. Glyph Atlas

Glyphs may be stored in a reusable GPU texture atlas.

The atlas is itself a content-addressed resource:

```rust
struct GlyphAtlasId(ContentHash);
```

A single glyph resource may be reused by many labels.

---

# 50. Label Size

Label size is evaluated in screen units.

A label intended to be 14 px remains approximately 14 px regardless of geographic scale.

Its position is derived from world/spherical geometry.

Its dimensions are derived from screen-space typography.

---

# 51. Label Placement Stability

The label engine shall retain previous placement.

Conceptually:

```text
previous placement
        ↓
is it still legal?
   ├── yes → retain
   └── no → recompute
```

The previous legal placement has priority over alternate placement.

The renderer shall not arbitrarily reshuffle labels every frame.

---

# 52. Label Hysteresis

Label stability shall be based primarily on retained placement state and legality, not arbitrary zoom thresholds.

Avoid rules such as:

```text
show at zoom 5.2
hide at zoom 5.0
```

unless explicitly specified by atlas style data.

Instead:

> A visible label remains visible until its retained placement ceases to satisfy the hard placement constraints.

---

# 53. Label Priority

Priority must be data-driven and deterministic.

Conceptually:

```rust
struct LabelPriority {
    layer_order: i32,
    semantic_importance: i32,
    feature_order: i64,
}
```

The exact priority values are data supplied by the style system.

The renderer must never use random or iteration-order-dependent selection.

---

# 54. Deterministic Label Placement

Given identical:

```text
SceneRevision
Camera
StyleRevision
PreviousPlacement
```

the placement engine must produce the same result.

This is required both for visual stability and automated testing.

---

# 55. Label Movement

If a retained placement becomes invalid, a new placement may be selected.

Where practical, its screen position should move continuously:

```text
old placement
      ↓
continuous movement
      ↓
new placement
```

rather than:

```text
old position disappears
      ↓
new position suddenly appears
```

Visibility fades are permitted for genuine label lifecycle transitions but should not conceal ordinary deterministic placement instability.

---

# 56. Label Visibility State

Conceptually:

```rust
enum LabelVisibilityState {
    Hidden,

    Appearing {
        start: Time,
    },

    Visible,

    Moving {
        from: Placement,
        to: Placement,
    },

    Disappearing {
        start: Time,
    },
}
```

Animation duration must be a declared system/style parameter, not an arbitrary implementation constant.

---

# 57. Hit Testing

Hit testing answers:

> Which semantic feature is under the user's click?

Examples:

```text
click on territory
    → FeatureId::Judah

click on city
    → FeatureId::Jerusalem

click on river
    → FeatureId::<river>
```

The renderer shall not depend on DOM/SVG event targets.

---

# 58. Hit-Test Identity

Every interactive map object shall retain its semantic:

```rust
FeatureId
```

The renderer maps screen-space input back to that identity.

---

# 59. Hit-Test Implementation

The first implementation may use CPU geometry tests.

For example:

```text
mouse position
    ↓
visible candidate resources
    ↓
screen-space / projected geometry test
    ↓
nearest or containing feature
    ↓
FeatureId
```

A later implementation may use a GPU picking pass:

```text
feature ID → offscreen pixel
```

Hit testing is event-driven and therefore does not need to execute fully on every animation frame.

---

# 60. Six Rendering Layers

The existing six layers remain:

```text
background
relief
scripture-claims
territory
water
journeys
```

They become retained GPU render passes.

The semantic order remains defined by the existing style/template system.

---

# 61. Styling

Styles remain data.

The rendering system may compile styles:

```rust
StyleId
    ↓
GpuStyle
```

but it may not invent semantic styling rules in code.

The GPU renderer consumes style data rather than deciding atlas aesthetics itself.

---

# 62. Parchment and Raster Assets

A small raster texture is appropriate for artistic substrate such as parchment.

This does not transform the atlas into a raster map.

The intended model remains:

```text
parchment texture
+
vector geographic geometry
+
GPU-rendered text
```

Vector geometry remains geographic truth.

---

# 63. Binary Transport

The GPU path shall use packed binary resource payloads rather than JSON geometry.

A conceptual resource packet:

```text
header
resource ID
content hash
resource kind
LOD metadata
spherical bounds
vertex count
index count
vertex payload
index payload
```

JSON may remain useful for:

* debugging;
* inspection;
* development;
* archival.

It should not be the high-frequency interactive geometry transport format.

---

# 64. Draw Items

The renderer constructs lightweight per-frame draw references:

```ts
interface DrawItem {
    resource: GpuGeometry;
    style: GpuStyle;
    feature: FeatureId;
    morph?: MorphState;
}
```

A draw item may be rebuilt every frame because visibility can change.

The underlying GPU resources are not rebuilt.

This is the distinction between:

```text
draw list
```

and:

```text
retained scene
```

---

# 65. Frame Rendering Contract

The renderer interface should conceptually be:

```ts
interface Renderer {
    setScene(scene: RetainedScene): void;
    setCamera(camera: Camera): void;
    draw(): void;
}
```

`setCamera()` must remain cheap.

Camera changes must not imply `setScene()`.

---

# 66. Resource Demand

The resource system shall distinguish:

```text
currently visible
```

from:

```text
worth retaining for imminent visibility
```

A demand envelope may account for:

```text
camera velocity
×
measured resource acquisition latency
```

rather than arbitrary pixel/tile margins.

All such quantities are measured and declared runtime/system parameters.

---

# 67. No Tuned Magic Constants

The implementation shall avoid arbitrary constants such as:

```text
PREFETCH_TILES = 3
LABEL_HYSTERESIS = 0.25
FADE_TIME = 150ms
KEEP_ALIVE = 10 frames
```

unless those values are first-class declared parameters with documented justification.

Existing project laws such as:

```text
half-pixel LOD
```

remain authoritative.

---

# 68. Runtime Capability Profile

Renderer behavior may depend on measured platform capabilities.

Conceptually:

```rust
struct RendererCapabilities {
    webgl2: bool,
    webgpu: bool,

    gpu_memory_bytes: Option<u64>,

    max_buffer_size: u64,
    max_texture_size: u32,

    display_refresh_hz: f32,

    measured_resource_upload_rate: BytesPerSecond,
    measured_decode_rate: BytesPerSecond,
    measured_server_latency: Duration,
}
```

These are capabilities and measurements, not hidden behavior constants.

---

# 69. 60 FPS

For a nominal 60 Hz display:

```text
frame period = 1 / 60 second
             ≈ 16.67 ms
```

The interactive renderer should fit camera update and normal drawing within the available frame period.

Server latency does not belong in this frame budget.

Network and decode activity is asynchronous.

---

# 70. Graphics Backend Abstraction

The graphics implementation should have a backend boundary:

```rust
trait GraphicsBackend {
    fn create_geometry(...);
    fn create_texture(...);
    fn create_pipeline(...);
    fn update_buffer(...);
    fn draw(...);
}
```

Initial implementation:

```text
WebGl2Backend
```

Future implementation:

```text
WebGpuBackend
```

No WebGPU implementation is required initially.

The interface simply prevents architectural lock-in.

---

# 71. MapLibre / Google-Earth-Class Principle

The relevant architectural principle from mature vector renderers is:

```text
persistent vector data
+
persistent GPU resources
+
persistent symbol/layout state
+
cheap camera transforms
```

rather than:

```text
server renders a new image for every camera position
```

The specification adopts that principle without adopting a planetary-scale engine.

The atlas does not need a full MapLibre/Cesium/deck.gl architecture.

---

# 72. Minimal Initial Implementation

The first production implementation should contain approximately:

# 73. Migration Strategy

Migration must be incremental.

The existing SVG viewer remains functional until the final stage.

---

## Stage 1 — Remove Bitmap Scaling

Retain SVG as the visual renderer.

During camera motion, transform the existing SVG rather than generating bitmap snapshots.

This is only a transitional improvement.

Goal:

> establish that camera motion is not a server-rendered-scene event.

The SVG remains the current implementation while the new retained architecture is developed.

---

## Stage 2 — Introduce GPU Scene Protocol

Add:

```rust
GpuSceneEncoder
```

alongside:

```rust
SvgEncoder
```

Produce:

```text
SceneManifest
ResourceDescriptor
binary geometry resources
```

without changing the SVG path.

Both encoders must consume the same styled scene.

---

## Stage 3 — Build Resource Cache

Implement:

```text
ResourceCache
ResidencyManager
```

using the simplest current implementation:

```text
resources remain resident
```

No eviction or tiling is required.

The viewer may still use SVG while this layer is tested.

---

## Stage 4 — Render One Vector Layer in WebGL2

Move one representative layer, preferably territory boundaries, to WebGL2.

This validates:

* spherical coordinates;
* projection;
* shared borders;
* GPU buffers;
* camera pan;
* camera zoom;
* LOD resource identity.

Everything else can remain in SVG temporarily.

---

## Stage 5 — Move Fills and Major Layers

Move:

```text
territory fills
water
relief
scripture-claims
journeys
```

to retained GPU resources.

The six semantic layers remain unchanged.

---

## Stage 6 — Move Labels to GPU

Implement:

```text
font data
glyph shaping
glyph atlas
label placement
GPU rendering
```

without changing typography semantics.

Styles remain data.

---

## Stage 7 — Add Continuous Geometry Refinement

Implement coarse → fine refinement for one geometry family.

Verify:

```text
same resource identity semantics
continuous transition
no parent disappearance
```

before extending to additional geometry classes.

---

## Stage 8 — Add Temporal Transitions

Implement:

```text
TemporalChange
TemporalTransition
CorrespondenceId
```

and keep the old historical scene drawable while new resources arrive.

---

## Stage 9 — Add Eviction

Introduce GPU eviction only after correctness is established.

Eviction shall be driven by:

```text
resource identity
retention references
measured capacity
```

not arbitrary feature-based rules.

---

## Stage 10 — Add Paging / Spatial Tiling

Only when dataset growth requires it should the resource implementation introduce:

```text
spatial pages
tile manifests
disk cache
network paging
```

The rendering interfaces remain unchanged.

---

## Stage 11 — Retire Interactive SVG

At this point:

```text
SvgEncoder
```

remains useful for export and archival.

The interactive viewer uses:

```text
GpuSceneEncoder
```

as its production renderer.

SVG is no longer the interactive rendering mechanism.

---

# 74. Validation Requirements

The architecture is not considered complete merely because it reaches 60 fps.

It must pass the following stability tests.

---

## Test A — Camera Target Continuity

Given:

```text
Scene S
Camera C₁
```

draw the scene.

Then continuously change:

```text
target C₁ → target C₂
```

without changing semantic scene state.

Assert that existing GPU resources remain valid.

---

## Test B — Zoom Continuity

Perform fractional zoom continuously.

Assert:

```text
no whole-scene resource replacement
```

and:

```text
no bitmap snapshot
```

---

## Test C — Combined Pan and Zoom

Perform simultaneous:

```text
target(t)
zoom(t)
```

motion.

Assert that both changes are represented solely through camera-state changes and asynchronous resource demand.

---

## Test D — Asynchronous Resource Delay

Delay a requested resource substantially.

During the delay:

```text
camera continues changing
```

and:

```text
frame rendering continues
```

with no blocking.

---

## Test E — Refinement Continuity

For parent `P` and child `C`, assert:

```text
render(C, progress=0)
≈
render(P)
```

within declared numerical tolerance.

Sample intermediate progress values:

```text
0
0.1
0.2
...
1
```

and verify continuity.

---

## Test F — Refinement Failure

Force a child resource to fail.

Assert:

```text
parent remains drawable
```

and:

```text
current image remains intact
```

---

## Test G — Content-Addressed Historical Reuse

Construct multiple snapshots referencing the same geometry hash.

Assert:

```text
one GeometryId
one GPU resource
multiple historical references
```

---

## Test H — Projection Independence

Render the same `GeometryId` under:

```text
orthographic globe
flat projection
```

and assert both use the same canonical geometry resource.

---

## Test I — Deterministic Labels

Given identical:

```text
SceneRevision
Camera
StyleRevision
PreviousPlacement
```

assert identical label-placement decisions.

---

## Test J — Label Stability

Move the camera continuously while a label's retained placement remains legal.

Assert that the label does not arbitrarily change anchor or disappear/reappear.

---

## Test K — No Global Enumeration

The client startup path shall not depend on receiving the full atlas.

The viewer must remain correct if only the currently demanded resources are available.

---

# 75. Formal Invariants

The following invariants should be encoded in tests and documentation.

### I1 — Camera Resource Stability

For a fixed semantic scene:

```text
camera change
→ no existing resource invalidation
```

except explicit eviction.

---

### I2 — Camera Target Is a First-Class State Variable

For every pan:

```text
target(t)
```

changes continuously according to camera-controller semantics.

Pan must never be represented as mutation of canonical map geometry.

---

### I3 — Camera Transform Does Not Change Canonical Geometry

For any point `p`:

```text
p before camera movement
=
p after camera movement
```

in canonical unit-sphere coordinates.

---

### I4 — Acquisition Is Asynchronous

No camera frame waits on resource acquisition.

---

### I5 — Resource Identity Is Content Identity

Equal content produces equal resource IDs.

---

### I6 — Temporal Reuse

Historical snapshots referencing the same canonical geometry share the same geometry resource.

---

### I7 — Projection Independence

Projection changes do not change canonical geometry identity.

---

### I8 — Refinement Continuity

Valid spatial refinements are continuous.

---

### I9 — Refinement Monotonicity

Spatial refinement cannot discontinuously erase already represented geometry.

---

### I10 — Residency Failure Safety

A refinement failure cannot invalidate the previously stable resource.

---

### I11 — Label Placement Stability

A valid previous placement remains preferred over arbitrary alternatives.

---

### I12 — Deterministic Placement

Equal inputs yield equal label-placement decisions.

---

### I13 — Visibility Is Not Residency

Resources may remain resident even when currently invisible.

---

### I14 — Client Does Not Assume Full Dataset Residency

The architecture remains valid for a paged implementation.

---

### I15 — Renderer Does Not Own Semantic Styling

Styles remain data-driven and independent of rendering backend.

---

# 77. The Core Concept

The final architecture can be summarized in one distinction:

```text
OLD

camera change
    ↓
new render request
    ↓
new SVG
    ↓
replace picture
```

versus:

```text
NEW

camera change
    ↓
Camera {
    target,
    zoom,
    viewport
}
    ↓
GPU transform
    ↓
draw retained resources
    ↓
optional asynchronous refinement
```

For a pan:

```text
target(t) changes
```

For a zoom:

```text
zoom(t) changes
```

For pan + zoom:

```text
target(t) and zoom(t) change
```

In all three cases:

```text
canonical geometry remains unchanged
retained GPU resources remain available
camera animation never waits for the server
```

The map therefore behaves as one continuously existing image rather than as a succession of replacement images.

**The camera moves; the map does not get rebuilt.
The map refines; it does not flash.
The data arrives; it does not invalidate what is already visible.**

That is the defining invariant of the rendering architecture.
